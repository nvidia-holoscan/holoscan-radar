- **2026-08-06** — **D22's application-level requirements were wrong and are withdrawn.** Eight documents claimed that composing with this module obliges an app to set `is_metadata_enabled(true)` and a fragment-wide `metadata_policy = kUpdate`. Neither holds in the installed SDK headers: metadata is **enabled by default** (`kDefaultMetadataEnabled = true`), and `metadata_policy` is **per-operator, taking precedence** over the fragment default. `kUpdate` is still mechanically forced, but for the one consumer merging several ports from a single producer — `BackprojectionOp` — which sets it on itself. Our own [SDK_QUESTIONS.md](SDK_QUESTIONS.md) had it right all along ("`MetadataPolicy` is per operator"); the SAR docs contradicted it.
- The correction matters beyond tidiness because it repriced an amendment under review: the metadata plane in **R1** was carrying a stated cost of two app-wide settings, and it actually costs the application nothing. What survives is a hazard rather than a requirement — a foreign operator with metadata *explicitly* disabled between the source and the control owner drops the boundary announcement, surfacing as `BackprojectionOp`'s `stop()` warning. [SAR/TESTING.md](SAR/TESTING.md)'s assertion is retargeted to match: not "the app set these", but "the module configures itself and degrades visibly when something external interferes."
- **2026-08-06** — **`BackprojectionOp.precision_mode` is renamed `backend`**, a contract change to a parameter name, closing **I6**'s naming half; the value set stays open until kernels exist and the frontier is measured. The old name claimed too little: the parameter selects a strategy of which precision is one consequence among throughput, memory and admissibility, some variants being valid only for planar scenes. The contract had already called the name provisional. Renaming is free now — no SAR code exists — and would not be later. Known residual: in a GPU library `backend` can read as a device selector, which it is not, so the parameter note says so. The old name stands in the two practitioner review records; I6 carries the mapping.

Revising the contract as implementation teaches us things is expected — explicit, not grudging — but **every revision is approved by the developer in the chat session before it is made**, SAR-scoped ones included, then tagged at the point of change and appended to a running log in [SAR/OPERATOR_API.md](SAR/OPERATOR_API.md) → *Contract changes since approval*. The gate is ask-first rather than report-after, and it extends to code: an implementation that would need a contract change stops and asks rather than proceeding and reconciling later. Typos, links and clarifying prose are not contract changes.

A revision reaching **beyond SAR** clears the same approval gate, is declared as beyond-SAR when asked, and additionally gets a reviewer-facing marker in the document plus a row in the module-wide [TEAM_BLOCKED.md](TEAM_BLOCKED.md) — which makes that file where FMCW owners see SAR work touching them, without reading SAR docs. Where a SAR-scoped and a beyond-SAR option both solve a problem, the SAR-scoped one wins by default; D24 is the worked example.

Since `D22`'s `stream_boundary` key is reached in phases 1 and 2 — the reader writes it, mode 1's control operator reads it — the standing instruction is to use `holoscan.radar.sar.stream_boundary` behind one named constant until the team rules, committing FMCW to nothing and leaving promotion a one-line change.
- **2026-08-07** — **`RangeMatchedFilterOp` is renamed `RangeReferenceMultiplyOp`, closing I3** — the first change logged under the post-acceptance gate in [SAR/OPERATOR_API.md](SAR/OPERATOR_API.md) → *Contract changes since approval*, SAR-scoped, approved in session. Name only: ports, parameters and algorithm are untouched, and the operator is a later wave with no code, so the change is 14 references across five documents.
- The old name was not merely unsettled. **Range-matched filtering is a standard term whose standard scope includes the inverse transform** — the RDA's three steps are conventionally range-matched filtering, RCMC and azimuth-matched filtering, with the range IFFT inside the first. So the name denoted this operator *plus* `SARRangeCompressionOp`, and a practitioner would rightly have expected range-compressed output from a stage that emits an un-inverted spectrum.
- Two things generalize past this operator. **Invariant 7 can be neutral rather than binding**, and I3 is the case: no source names the truncated stage, because outside a split pipeline nobody stops there, so there was no term to adopt and the invariant neither supplied a name nor endorsed the one we had. A standard term used with a non-standard scope is *worse* than a coined one, since it looks familiar and misleads.
- The replacement is built from the literature's term for the operand — the **range reference function** — consistent across the ASF training processor, the ERS MATLAB processors and the FPGA range-Doppler implementations. `SARRangeCompressionOp` deliberately keeps its name: on the CPHD path, the only wave-one ingress, the data is already deramped phase history and range compression genuinely is the transform alone.
- **2026-08-07** — **Implementation is prioritized as the shortest path to a working mode 1 demo**, at the developer's direction, and [SAR/SIGPROC_PLAN.md](SAR/SIGPROC_PLAN.md)'s phases 0–2 are rewritten around that. The path is shorter than the phase table implied: **mode 1 needs three library operators, not nine** — `CPHDReaderOp`, `SARRangeCompressionOp`, `BackprojectionOp` — plus `TensorDumpOp` and a small control operator in the app's `custom_ops.hpp`. `ApertureManagerOp` is off it entirely, because a spotlight retains nothing and evicts nothing, which is the case *Running without a manager* was written for.
- Mode 1 also leaves `weight`, `sample_points` and `initial_image` unconnected and takes the default `interpolation`, `backend` and `geometry_change`, so most of `BackprojectionOp`'s surface goes untouched by the first demo. Four things moved out of the early phases as a result, and one costs something real: **`CPHDWriterOp` and the round-trip test are deferred**, removing the reader's field-interpretation check from exactly the stretch where the reader is newest. The substitutes are `sarpy` reading back the simulator's output and the end-to-end MatX golden, which catches a reader error but localizes it poorly.
- The other three deferrals are cheap: three of the four pinned collections (Atlanta is `CF8` with no `AmpSF`, so phase 1 implements one decode path), `ApertureManagerOp`, and the non-default backends, points-mode geometry, signed weights and scroll. **The point-target simulator stays on the path** and ahead of real data, because a wrong-convention trajectory produces a plausible image — so a fixture with an analytically predicted pixel is what makes a bug visible rather than merely suspected.
- **The demo is signed off in two stages.** Phase 2 dumps the formed image and renders it to a PNG offline, and that image is agreed correct **before** any Holoviz work starts — rasterization and layout are effort spent making a correct image presentable, and spending it first risks debugging formation through a display pipeline. Holoviz moves from the products slice up into phase 2, behind that checkpoint.
- **The rule is now standing, not a one-off.** The wave **grows by doing the minimum required for the next working application**: each slice delivers one demo and stops, and work is scheduled against the demo that first *forces* it. Phases 0–2 are that rule applied to mode 1; everything after is re-derived the same way, and the slices after phase 2 are **named for their demo** rather than numbered, since a phase number beside a mode number invited the confusion the skipped "phase 5" already guarded against. Mode 5 is sequenced *before* mode 4 because it re-runs the mode 1 and mode 3 collections and so costs a YAML.
- Re-deriving caught a real misalignment. The old phase 3 bundled the deferred reader paths with mode 2, but **Houston is Umbra `CF8` without `AmpSF` — the same decode path Atlanta already forced — so video SAR needs no reader work at all.** `CI4`, `AmpSF`, the second CPHD minor version and the two unverified Capella keys are forced by **mode 3**, one demo later, and open item 3 in [SAR/INPUT_DATA.md](SAR/INPUT_DATA.md) moves with them. The reader will look finished two demos before it is, which is the sharpest place this rule bites.
- The rule's honest cost is that some work is forced by **no** first-ship demo, so a strict reading lets it drift. Three items are named and scheduled into the Products slice rather than left to chance: the `CPHDWriterOp` round trip (with "reader bugs bite during modes 1–3" recorded as the trigger to pull it forward), the three non-default `backend` values, which only the performance harness can distinguish, and points-mode `sample_points`, first genuinely needed by mode 9.
- **2026-08-08** — **SAR phase 0 lands: the first SAR code in the repository.** Four deliverables, all as specified — the three new descriptors (`CoordinateFrame`, `SampleGeometry`, `LFMWaveformDescriptor`) in `operators/common/radar_common/descriptors/`, the grid-expansion helper `dsp/sample_lattice.hpp`, `operators/sar/` + `operators/io/` scaffolding, and the in-repo simulator with the mode 1 point-target recipe. Invariant 2's amended count of **nine** descriptors is now true in code as well as in the contract. **No contract change was needed**, which is the useful signal: the specification survived first contact with implementation intact.
- **The phase's real product is a verified convention chain, not the descriptors.** CPHD's deramped phase history has a sign, `Global/SGN` declares it, the image axes have an orientation, and the ground-range projection has a cosine in it — and every one of those fails *silently*, because a mirrored image of a plausible scene is a plausible image. So `tests/python/sar/test_sar_sim.py` backprojects the generated fixture with an **independent** reference implementation and asserts each target lands on the pixel the sidecar predicts. It does, with amplitudes tracking the recipe. Every later SAR assertion stands on that fixture, so the sidecar's predicted indices had to be established by something other than the simulator agreeing with itself.
- Two conventions are now pinned that `CPHDReaderOp` will meet in phase 1. **The frequency-to-delay transform takes the positive-exponent kernel** — numpy's `ifft`, not `fft`; the conjugate mirrors every target about the reference point. And **CPHD signal arrays are big-endian regardless of host**, so the reader byte-swaps on every machine it will realistically run on; a test asserts it so the requirement keeps being stated.
- **What the simulator cannot establish is agreement with the outside world**, and that gap is real rather than theoretical. Everything above is self-consistency: the phase model, the declared `SGN`, and the reference backprojector are three statements of one convention, and all three being wrong together is exactly as consistent as all three being right. The **phase 2 Atlanta comparison against the MatX golden is what closes it**, which is a second reason that milestone matters beyond producing a pretty image. If the fixture and the real collect disagree there, suspect this before suspecting the operator.
- Two implementation choices worth knowing, neither a contract change. `CoordinateFrameType` carries a `kUnspecified` sentinel so the spec struct is default-constructible and construction can reject a missing frame — the established `MultiplexingScheme::kUnspecified` pattern, and deliberately **not spellable in YAML**. And the simulator lives in a new top-level **`tools/sar_sim/`** rather than under `python/holoscan/radar/`, keeping `sarpy` / `sarkit` out of the shipped package namespace as [SAR/INPUT_DATA.md](SAR/INPUT_DATA.md)'s policy requires; the subsetter joins it there. [AGENTS.md](../../AGENTS.md)'s repo map gains rows for all three new directories.
- Sizes, for scheduling the next slices: the CI smoke fixture is 1.1 MiB and generates in under a second; the mode 1 demo fixture is 32 MiB in one second, on a 693 x 525 lattice at 0.25 m slant range and 0.38 m azimuth. Both are airborne X-band rather than spaceborne, because a satellite geometry needs either a six-figure pulse count or an implausible PRF to reach the same integration angle at fixture size — the scene frame is still Atlanta's, so the demo YAML is reusable.
- **2026-08-08** — **The CPHD subsetter moves off phase 2 and onto the mode 2 slice**, which takes all pull tooling off the mode 1 critical path. The subsetter's two jobs are a pulse window and a contiguous central frequency subband, and mode 1 needs neither: `CPHDReaderOp.pulse_range` already selects an aperture out of a long collection, and a spotlight has no reason to narrow bandwidth, since full bandwidth *is* the finest range resolution it wants. Atlanta at 28.59 GiB can therefore be pulled whole and read with `pulse_range`. Houston at 110 GiB cannot, and its subband is a strided slice inside every vector rather than a contiguous byte range — 208,753 range requests — so mode 2 forces the tool regardless.
- The mis-scheduling came from **conflating the demo with the parity check**. Phase 2's demo runs on the generated `mode01` fixture; Atlanta appears only as the MatX golden. Every user runs the first and a developer runs the second once, so a 28.59 GiB pull is unreasonable for one and unremarkable for the other, and bundling them made the subsetter look load-bearing a demo earlier than it is. Sequencing only, no contract change: `pulse_range` is used exactly as specified.
- Worth carrying forward as a check on the minimum-per-demo rule itself. The rule schedules work against the demo that first *forces* it, and both errors it has caught so far — the Capella reader paths, now this — were **tooling assumed to be needed earlier than the first demo that actually forces it**. Asking "which demo breaks without this?" is what found both, and it is cheaper to ask than to build.
