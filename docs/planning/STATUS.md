Chosen over adding a bare-scalar (`epsilon: 0.5`) YAML/Arg converter: the `[list]` idiom is already uniform across every vector parameter (`guard_cells`, `training_cells`, `nci_axes`, `spatial_smoothing`), so ratifying it is the consistent choice, whereas a scalar special case for `epsilon` alone is inconsistent and invites the same converter everywhere (scope creep for a cosmetic gain). Docs-only — `OPERATOR_API.md` `epsilon` bullet tightened to state the one-element-list convention | 2026-07-22 |
| L7 — ClusterDBSCAN `max_clusters` surplus policy | **Keep the largest clusters** — realized by numbering ids by descending size (L10), so the existing "drop highest ids" cap drops the **smallest** surplus clusters (their points → noise `-1`, keeping `labels`/`sizes` consistent). Chosen over the prior spatially-arbitrary ascending-root drop, and over "leave surplus `labels` populated / truncate only `sizes`" (**rejected** — breaks the `sizes[label]` invariant). `OPERATOR_API.md` `max_clusters`/`sizes` updated; landed + tested (`MaxClustersKeepsLargest`, C++ + Python). No configurable ordering parameter is planned | 2026-07-22 |
| L10 — ClusterDBSCAN cluster-id numbering order | Pin **descending point count** (cluster 0 = largest), ties broken by **ascending component root** (lowest member row index); `sizes` non-increasing. Chosen over the prior ascending-root numbering — descending size gives a "cluster 0 is largest" guarantee and makes the `max_clusters` cap keep the largest (L7) for free. Deterministic (`labels` a pure function of `(points, epsilon, min_points)`). Implemented via a host argsort of per-id counts + a `remap_labels` GPU pass; `OPERATOR_API.md` `labels`/`sizes` updated; tested (`NumbersClustersByDescendingSize`). No `cluster_order` parameter is planned | 2026-07-22 |
| L6 — CFAR exact-sized `detection_idx` | **Ratify exact sizing** (chosen over a capacity + `num_detections` port). | L16 — Exact `[live]` join | **Adopt Exact{}** against the data trigger's `capture_time` for every enabled `[live]` port.
