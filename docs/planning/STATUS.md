- **2026-08-07** — **`RangeMatchedFilterOp` is renamed `RangeReferenceMultiplyOp`, closing I3** — the first change logged under the post-acceptance gate in [SAR/OPERATOR_API.md](SAR/OPERATOR_API.md) → *Contract changes since approval*, SAR-scoped, approved in session. - The old name was not merely unsettled. **Range-matched filtering is a standard term whose standard scope includes the inverse transform** — the RDA's three steps are conventionally range-matched filtering, RCMC and azimuth-matched filtering, with the range IFFT inside the first. So the name denoted this operator *plus* `SARRangeCompressionOp`, and a practitioner would rightly have expected range-compressed output from a stage that emits an un-inverted spectrum.
- Two things generalize past this operator. **Invariant 7 can be neutral rather than binding**, and I3 is the case: no source names the truncated stage, because outside a split pipeline nobody stops there, so there was no term to adopt and the invariant neither supplied a name nor endorsed the one we had. - The replacement is built from the literature's term for the operand — the **range reference function** — consistent across the ASF training processor, the ERS MATLAB processors and the FPGA range-Doppler implementations. `SARRangeCompressionOp` deliberately keeps its name: on the CPHD path, the only wave-one ingress, the data is already deramped phase history and range compression genuinely is the transform alone.

The parser's positions, times, frequency axis and per-pulse power match `sarkit` to full double precision, which pins the byte order and the block offsets independently of our own writer. - **D22's metadata correction is confirmed in the SDK source**: `kDefaultMetadataEnabled = true` and `kDefaultMetadataPolicy = kRaise` in `holoscan/core/fragment.hpp`, so no application-wide enable is needed. The doc comment on `Operator::metadata()` still claims metadata is off unless the fragment enables it — that comment is stale, and it is the kind of thing that would have been taken at face value had the question not already been settled.
- **`kRaise` bites immediately and exactly where the contract predicted.** A consumer taking three ports from one reader merges the same boundary key three times, and the graph fails until that operator sets `kUpdate` — operator-level, per D22, not application-wide. Every multi-port consumer of the reader, `BackprojectionOp` and the mode 1 control operator included, will need the same one line.
- **One read of the parameter block per tick, not one per field.** The first cut called `read_pvp` eight times a tick — `TxPos`, `RcvPos`, `SRPPos`, `SC0`, `SCSS`, `TxTime`, `TxVel`, `RcvVel` — each bulk-reading the same interleaved bytes, because PVP records store all fields together. `read_pvp_block` reads the span once and hands out fields from host memory. Measured against `/proc/self/io` on both fixtures: exactly **8.00x** fewer bytes through `read()`, identical values. Worth noting the overhead scaled with the sample count rather than being fixed — about 11% on top of the signal read for the 2048-sample demo fixture, but 44% for the 512-sample smoke one, since the parameter record is the same size either way.
- **And the signal was copied three times a tick, one of them a no-op.** Raw bytes, byte-swapped `complex<float>`, then a "narrowing" to `complex<T>` that for a `CPHDReaderOp<float>` instance was `static_cast<float>` on a `float`. The cause was an interface seam: `read_signal` hardcoded `complex<float>` while the operator is templated, so the operator converted even when there was nothing to convert. `read_signal_into` reads at the caller's precision into the caller's buffer, and since CF8 is bit-for-bit big-endian `complex<float>` a single-precision instance now byte-swaps in place with **no** intermediate copy — **6.03x** faster per tick on the 2048x2048 fixture, a third of the peak buffer, identical values.
- **Worth generalizing:** both of this operator's performance bugs were interface seams rather than slow code — a return type that forced a copy, and a per-field API over a per-record file layout. Neither is visible in either function alone; both are visible the moment the call site is read next to the callee.
- **`tinyxml2` is the CPHD XML dependency**, linked `PRIVATE` and named by no public header, so a build with `OP_cphd_reader_op` off never looks for it — the containment the `io` group was created for.

- **2026-08-12** — **Moving the MatX pin on its own, to get `sar_bp` without an SDK upgrade, was measured end to end and then paused by the team** until the Holoscan 5.0 conversion lands on `main`, since 5.0 moves the pin anyway. No module code changed: the experiment ran in a throwaway build tree against a MatX installed under `/tmp`. Full evidence is under **I1** in [SAR/OPERATOR_API.md](SAR/OPERATOR_API.md) → *Open items*, and the standing "do not bump MatX" instruction in [SAR/SIGPROC_PLAN.md](SAR/SIGPROC_PLAN.md) now cites the team decision rather than an assumed cost. The point of recording a paused experiment is that the next person inherits the answer instead of the question.
- **Holoscan does not depend on MatX at all, which is what made the rest cheap.** Checked first because everything else hinged on it: `libholoscan.so` exports zero MatX symbols, and the single SDK header naming MatX is duck-typed to its allocator interface, includes no MatX header, and is unreachable from `holoscan.hpp`. So the bundled MatX is a convenience drop and the pin was always this module's alone — one `-DMATX_DIR=` redirects every target, no CMake edit and no vendoring. The instinct that this need not wait for an SDK upgrade was right; the reason it still waits is different from the reason anyone expected.
- **800 errors at C++17, zero at C++20, and not one of them in module code.** Every failure sat inside MatX's own headers — `concept` and `requires` undefined, `std::format` and `std::source_location` missing — because MatX 1.0.0 declares `cxx_std_20` where this module pins 17. That reframes the whole question: it is not an API migration to be worked through file by file, it is one language-standard bump that either is acceptable module-wide or is not. Worth knowing for anyone bumping MatX anywhere: the CUDA half of the requirement is `$<BUILD_INTERFACE:cuda_std_20>`, so it does **not** reach consumers and `.cu` files silently stay at the caller's `CMAKE_CUDA_STANDARD`.
- **At C++20 the tree builds clean and 566 of 567 unit tests pass**, the lone failure a zero-length `.so` a host reboot truncated mid-link, which relinked fine. The Python suite is the one surface left unverified. The expected casualty was `mvdr_stage.hpp`, the module's only reach into `matx::detail` (eig/inv cache clearing plus the `GetAllocMap` drain) and exactly the kind of internal surface a major version is entitled to move — it survived untouched. A full build took 6m02s; no clean C++17 baseline was captured, so **no slowdown factor is claimed** rather than one being estimated.
- **What this hands the 5.0 conversion.** That conversion inherits the C++20 bump whether or not anyone plans for it, and the evidence says this module is ready. It also does not close I1: at 5.0's pinned commit `sar_bp` is still in `namespace experimental`, and it offers `Double`/`Mixed`/`FloatFloat`/`Float` but no `TaylorFast` — so the `taylor` member of I6's backend set needs a portable-kernel port no matter which MatX is in the build.

## Roadmap (deferred capabilities)

Capabilities deliberately **out of the current scope** — settled as deferred (no
current consumer / larger project), not blocked. Each is enforced today with a
clear error or documented limitation; pick one up when a concrete consumer
needs it.

| Capability | Why deferred | Where tracked |
| --- | --- | --- |
| **Staggered / non-uniform TDM schedules** (varying TX dwell or count) | Needs a per-TX-timing schedule descriptor **and** a generalized `MIMOCoherentCompensationOp` model (the compensation for arbitrary timing is an open design question). Uniform round-robin covers the FMCW workflows; non-uniform is rejected with a clear error today. Settled L12 | [MIMODeinterleave OPEN_ITEMS B.1](../../operators/fmcw/mimo_deinterleave_op/OPEN_ITEMS.md) |
| **Sum-set ("Harnessing Holes") holey subarray smoothing** | S3 selects a contiguous filled ULA/URA today; a sum-set decomposition (`S_b + S_c`, keeping holes for aperture when the array is sum-set smoothable) would recover more DOF / aperture from holey MIMO co-arrays. Research item — no consumer, and the gridless estimators (Root-MUSIC/ESPRIT) aren't built yet. Settled L14 (fork 3) | [SubarraySelection OPEN_ITEMS](../../operators/angle_estimation/subarray_selection_op/OPEN_ITEMS.md) |
| **`CoordinateFrame` for the FMCW operators** | The descriptor is SAR-only today, and deliberately so: invariant 6 keeps FMCW entirely in the array-local frame, so there is no second frame for a declaration to disambiguate and adding one would be ceremony. It becomes real the moment platform motion or geolocation enters the FMCW side — a moving-platform automotive or airborne configuration, or any product that has to be placed on a map. Revisit once SAR lands and the descriptor has been exercised against real collections | [SAR/OPERATOR_API.md](SAR/OPERATOR_API.md) → Supporting data structures → CoordinateFrame |
| **`sinc` / `nearest` backprojection interpolation** | `BackprojectionOp` implements `linear` only. The reference implementation spans ~48 tuned kernel variants and every one interpolates with two taps, because the interpolation is phase-controlled (envelope interpolated, carrier phase applied from the exact range) and `SARRangeCompressionOp.nfft` oversampling already buys impulse-response quality upstream. Both values are named in the enum and rejected with a clear error today, so implementing either later is a behavior change on a previously-erroring value rather than a contract break | [SAR/OPERATOR_API.md](SAR/OPERATOR_API.md) → BackprojectionOp → Notes |
